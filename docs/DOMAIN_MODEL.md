# Thermora Core — Domain Model

**Версия документа:** 1.1  
**Статус:** актуализирован по реализованному ядру; расширения отмечены отдельно  
**Платформа:** Kotlin/JVM, JDK 21  
**Назначение:** предметная модель физических величин, геометрии и условий теплового расчёта радиоэлектронной аппаратуры.

---

## 1. Назначение и границы

Domain Model определяет физический язык Thermora: величины и единицы измерения, геометрические характеристики, источники тепловыделения, условия окружающей среды и параметры теплообмена.

Ключевые правила:

- физические значения имеют явную размерность и согласованные единицы измерения;
- предметные объекты не зависят от UI, Excel, БД, транспорта и инфраструктуры;
- предметная модель не реализует эмпирические формулы конкретных расчётных методик;
- ограничения универсальных физических объектов отделены от ограничений применимости конкретной модели;
- Legacy и Improved модели могут использовать общие физические объекты, но не обязаны иметь одинаковые входные DTO.

**Текущая область:** базовые стационарные тепловые расчёты. Полная система материалов, тепловых сетей, переходных процессов и пространственного численного моделирования пока не реализована.

## 2. Модульная организация

```text
foundation/
├── common/   # Общие результаты и диагностика, не физическая предметная модель
├── units/    # Размерности, единицы и типизированные температурные величины
└── domain/   # Геометрия, среда, тепловые источники и условия вентиляции
```

Фактический корневой пакет исходного кода: `com.thermora.foundation`.

- `foundation:units` не должен зависеть от конкретных физических моделей.
- `foundation:domain` использует типы `foundation:units`.
- `models:*` используют предметные объекты и задают собственные расчётные входы/выходы.
- `calculation:api` задаёт контракты выполнения, а не определения физических величин.

Список ниже описывает **известные реализованные классы**, а не гарантирует исчерпывающий перечень файлов в репозитории. Перед фиксацией документа в Git следует сопоставить его с текущими исходниками.

## 3. Размерности и единицы измерения (`foundation/units`)

### 3.1. `PhysicalDimension`

`com.thermora.foundation.units.dimension.PhysicalDimension` описывает размерность через показатели базовых величин СИ:

| Основа | Символ |
|---|---|
| Длина | L |
| Масса | M |
| Время | T |
| Электрический ток | I |
| Термодинамическая температура | Θ |
| Количество вещества | N |
| Сила света | J |

Производные размерности, в том числе площадь, объём, мощность и тепловое сопротивление, выражаются комбинациями базовых показателей. Совпадение единиц по названию не заменяет проверки физической размерности.

### 3.2. `MeasurementUnit` и `StandardUnits`

`com.thermora.foundation.units.unit.MeasurementUnit` содержит символ, размерность, масштаб преобразования и, где требуется, смещение относительно базовой единицы.

`StandardUnits` предоставляет именованные единицы, используемые ядром. В текущих расчётах применяются, в частности:

| Величина | Единица СИ | Пример использования |
|---|---|---|
| Длина | m | Размеры нагретой зоны |
| Площадь | m² | Площадь поверхности и радиатора |
| Мощность | W | Тепловыделение |
| Температура | K | Абсолютная температура |
| Тепловое сопротивление | K/W | Переход–корпус, корпус–радиатор |

Также реализованы распространённые кратные единицы длины, площади, массы, времени и давления. Полный актуальный перечень следует сверять с `StandardUnits.kt`.

### 3.3. `Quantity`

`com.thermora.foundation.units.quantity.Quantity` объединяет численное значение с единицей измерения. Значение в согласованных базовых единицах доступно через `baseValue`.

При создании доменных объектов и при вычислениях требуется проверять ожидаемую размерность. Например, параметр мощности не должен принимать длину, даже если оба представлены числом `Double`.

**Численная безопасность:** проверки размерности не заменяют проверки конечности значений и промежуточных вычислений. Для моделей необходимо отдельно обрабатывать `NaN`, бесконечности, переполнения, деление на ноль и выход из области применимости.

## 4. Температура и температурная разность

В `foundation/units` реализованы отдельные типы:

- `com.thermora.foundation.units.temperature.Temperature` — абсолютная температура;
- `com.thermora.foundation.units.temperature.TemperatureDelta` — разность температур;
- `TemperatureUnit` — преобразования между K, °C и °F.

Принципиальное различие:

\[
T_K = T_{°C} + 273.15
\]

\[
\Delta T_K = \Delta T_{°C}
\]

Абсолютную температуру нельзя складывать с другой абсолютной температурой как обычную разность. Разность температур должна передаваться типом `TemperatureDelta`, а не маскироваться под `Temperature`.

В реализованной Legacy-модели используется корректное преобразование **273.15**, даже если в исходном Excel для отображения использовалось вычитание **273**. Это сознательно документируемое отличие представления, не скрытая замена эмпирических формул.

Пример создания абсолютной температуры:

```kotlin
val ambient = Temperature.fromKelvin(313.0)
```

## 5. Геометрия (`foundation/domain`)

Пакет: `com.thermora.foundation.domain.geometry`.

Реализованные предметные типы:

| Тип | Назначение |
|---|---|
| `EnclosureGeometry` | Геометрия корпуса |
| `Wall` | Стенка корпуса |
| `WallOrientation` | Ориентация стенки |
| `FinGeometry` | Геометрия оребрения |
| `PerforationGeometry` | Геометрия перфорации |
| `HeatSourceGeometry` | Геометрия нагретой зоны / источника тепла |

Геометрические характеристики следует хранить как размерные величины. При расчёте площади или объёма должны быть явно определены используемые поверхности и физические допущения.

**Важно:** `HeatSourceGeometry` не означает универсальную геометрию любого электронного компонента. В первой Legacy-модели объект используется для описания нагретой зоны, включая коэффициент заполнения. Специфический способ вычисления эффективной площади остаётся внутри модели.

Не следует добавлять в базовый `EnclosureGeometry` поля, необходимые только для одного варианта охлаждения.

## 6. Тепловые характеристики (`foundation/domain`)

Пакет: `com.thermora.foundation.domain.thermal`.

| Тип | Назначение |
|---|---|
| `ThermalSource` | Источник тепловыделения |
| `ThermalResistance` | Тепловое сопротивление |
| `CriticalElementThermalProperties` | Параметры критического элемента, включая мощность и тепловые сопротивления |

`CriticalElementThermalProperties` объединяет параметры, необходимые для оценки температуры критического элемента. В частности, сопротивления «переход–корпус» и «корпус–радиатор» не должны объединяться с сопротивлением корпуса окружающей среде: это разные физические участки теплообмена.

Общие инварианты объектов должны проверять размерности и базовые ограничения. Проверки, зависящие от конкретной эмпирической формулы, должны выполняться в соответствующей расчётной модели.

## 7. Условия окружающей среды и вентиляции

### 7.1. Окружающая среда

Пакет: `com.thermora.foundation.domain.environment`.

`AmbientConditions` описывает условия окружающей среды, используемые расчётной моделью. В первом реализованном сценарии основным параметром является абсолютная температура окружающей среды.

### 7.2. Вентиляция

Пакет: `com.thermora.foundation.domain.ventilation`.

Реализованы:

- `AirflowConditions` — условия воздушного потока;
- `FanSpecification` — характеристики вентилятора.

Эти типы предназначены для последующих моделей внутреннего перемешивания и принудительного охлаждения. Их наличие **не означает**, что соответствующие расчётные алгоритмы уже реализованы.

Внутреннее перемешивание и внешний обдув — разные физические сценарии; для них нельзя автоматически использовать одинаковые корреляции теплоотдачи.

## 8. Использование Domain Model в первой Legacy-модели

Реализованный модуль: `models/sealed-housing-legacy`.

Входной DTO `SealedHousingLegacyInput` использует следующие предметные типы:

```kotlin
// Схематическое представление фактического контракта
// (импорты опущены)
data class SealedHousingLegacyInput(
    val ambient: AmbientConditions,
    val source: ThermalSource,
    val heatedZone: HeatSourceGeometry,
    val criticalElement: CriticalElementThermalProperties,
    val elementWithRadiatorArea: Quantity
) : CalculationInput
```

Выходной DTO `SealedHousingLegacyOutput` содержит:

- абсолютные температуры корпуса, нагретой зоны, внутреннего воздуха, элемента и перехода;
- температурные превышения корпуса и нагретой зоны;
- тепловые сопротивления корпуса и нагретой зоны относительно окружающей среды.

Абсолютные температуры представлены `Temperature`, превышения — `TemperatureDelta`, сопротивления — `ThermalResistance`.

Физические формулы, численные коэффициенты и вычисление эффективной площади нагретой зоны принадлежат `SealedHousingLegacyModel`, а не `foundation/domain`.

### 8.1. Разделение ответственности

```text
foundation/units        → размерности, единицы, температуры
foundation/domain       → физические параметры и объекты
models/sealed-housing-* → конкретные формулы и ограничения модели
calculation/api         → контракт выполнения модели
calculation/engine      → регистрация, диспетчеризация и обработка результата
application/core        → прикладной фасад и стандартная конфигурация
```

Это логическая схема ответственности, а не перечень обязательных прямых Gradle-зависимостей каждого модуля.

## 9. Валидация и физическая допустимость

Проверки разделяются на четыре уровня:

1. **Размерностные:** например, мощность должна иметь размерность W.
2. **Доменные:** базовые ограничения физических объектов и величин.
3. **Модельные:** условия применимости эмпирических зависимостей, отношения площадей, диапазоны параметров.
4. **Численные:** конечность результатов, переполнения и устойчивость операций.

Успешное вычисление не является доказательством физической достоверности результата.

Для `sealed-housing-legacy` сохраняется предупреждение `SEALED_LEGACY_APPLICABILITY_UNKNOWN`: область применимости эмпирической методики пока не подтверждена. Предупреждение не следует удалять только потому, что регрессионные тесты проходят.

## 10. Соответствие исходной Excel-книге

Исходный файл: `docs/calculations.xlsx`.

Книга является источником **Legacy-алгоритмов**, но не диктует структуру предметной модели. Для каждой переносимой методики следует документировать:

| Элемент аудита | Что фиксируется |
|---|---|
| Источник | Лист и адрес ячейки Excel |
| Вход | Название, единица, допустимые значения |
| Преобразование | Перевод в СИ и обработка температур |
| Формула | Исходное выражение, коэффициенты, порядок операций |
| Выход | Физический смысл, размерность, тип результата |
| Проверка | Эталонные данные, допустимая численная погрешность |
| Ограничение | Неизвестная область применимости, допущения, расхождения |

В первой модели перенесена **выбранная ветвь** расчёта герметичного корпуса. Нельзя трактовать это как реализацию всей Excel-книги.

Legacy-модель сохраняет исходную вычислительную логику, а обнаруженные недостатки методики документируются отдельно. Исправленные физические корреляции следует размещать в самостоятельной Improved-модели.

## 11. Тестирование предметной модели

Для `foundation/units` и `foundation/domain` реализованы unit-тесты; сборка и тесты проекта ранее проходили успешно.

Основные категории тестов:

- соответствие размерностей и преобразований единиц;
- преобразование K/°C/°F и различение абсолютной температуры и температурной разности;
- ограничения геометрии и тепловых характеристик;
- допустимость условий окружающей среды и вентиляции;
- граничные случаи, `NaN` и бесконечные значения там, где они применимы;
- интеграционное использование доменных типов в `sealed-housing-legacy`.

Эталонные результаты Excel и интеграционные тесты `calculation/engine` дополняют, но не заменяют unit-тесты предметных объектов.

## 12. Запланированные расширения (не реализованы в текущем срезе)

Следующие возможности остаются проектными и **не должны восприниматься как существующие классы**:

- каталог материалов с температурно-зависимыми свойствами;
- происхождение входных данных (`ParameterSource`, `ParameterValue`) и неопределённости измерений;
- универсальная сериализация и версионирование схем;
- сравнение результатов Legacy/Improved с учётом физических предпосылок;
- переходные тепловые процессы;
- пространственное распределение температуры, тепловые сети и численные сеточные методы;
- специализированные входные структуры для новых Legacy/Improved моделей.

Добавлять такие абстракции следует при появлении реального расчётного сценария, а не заранее ради полноты схемы.

## 13. Архитектурные ограничения

1. `foundation/domain` не импортирует `calculation/engine`, `application/core`, Desktop или Spring Boot.
2. В доменных классах нет формул, принадлежащих отдельной Legacy-методике.
3. Система единиц и абсолютных температур остаётся единой для всех моделей.
4. Входные и выходные DTO моделей не подменяют универсальные физические объекты.
5. Данные из Excel преобразуются на соответствующей границе импорта или подготовки входа.
6. Модельные ограничения не должны без необходимости становиться глобальными инвариантами всех физических объектов.
7. Изменения, влияющие на результат Legacy-расчёта, требуют отдельного обоснования и регрессионной проверки.

## 14. Открытые вопросы

Перед реализацией следующих моделей необходимо уточнить:

- какие параметры Excel действительно общие для нескольких расчётных сценариев;
- какие геометрические структуры можно переиспользовать без потери физического смысла;
- нужны ли дополнительные единицы и производные размерности;
- как представлять происхождение параметров и версионирование сохранённых расчётов;
- какие диапазоны применимости эмпирических формул можно подтвердить;
- как формализовать сравнение результатов разных моделей.

## Итог

**Domain Model Thermora** — независимый от UI и расчётных методик слой физических понятий. В текущей реализации его основой являются `PhysicalDimension`, `MeasurementUnit`, `Quantity`, `Temperature`, `TemperatureDelta` и специализированные объекты `foundation/domain`. Новые физические модели должны расширять этот язык только там, где это обосновано их входными параметрами и физическим смыслом.
