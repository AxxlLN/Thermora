# Thermora Domain Model

**Статус:** проектируемая предметная модель  
**Язык:** Kotlin  
**Платформа:** JVM  
**Назначение:** описание предметной области тепловых расчётов радиоэлектронной аппаратуры.

---

## 1. Назначение

Domain Model определяет основные понятия, сущности, физические величины и правила представления данных, используемых в Thermora.

Предметная модель должна обеспечивать:

- единообразное представление физических величин;
- однозначное определение единиц измерения;
- разделение физических объектов и расчётных моделей;
- типобезопасное представление исходных параметров;
- сохранение происхождения исходных данных;
- единообразное представление результатов;
- возможность проверки физических ограничений;
- совместимость Legacy и Improved моделей там, где совпадает физический смысл данных.

Domain Model не должна зависеть от пользовательского интерфейса, базы данных, Excel, PDF или конкретной реализации расчётного алгоритма.

## 2. Границы предметной области

Thermora предназначена для выполнения тепловых расчётов радиоэлектронной аппаратуры (РЭС).

В рамках предметной области выделяются следующие основные группы понятий:

1. **Физические объекты** — корпуса, элементы аппаратуры, материалы и источники тепловыделения.
2. **Геометрические характеристики** — размеры, площади, объёмы и толщины.
3. **Тепловые характеристики** — температура, мощность, теплопроводность, тепловое сопротивление.
4. **Условия эксплуатации** — температура окружающей среды, параметры охлаждения и условия теплообмена.
5. **Исходные параметры** — значения, используемые при выполнении расчёта.
6. **Расчётные результаты** — вычисленные температуры, тепловые сопротивления и другие характеристики.
7. **Происхождение данных** — источник, способ получения и достоверность исходных значений.

Эти понятия не следует объединять в одну универсальную сущность. Например, геометрия корпуса и условия внешнего охлаждения являются разными группами характеристик, даже если обе используются одной расчётной моделью.

## 4. Физические величины и единицы измерения

### 4.1. Общие требования

Все физические величины должны иметь однозначную семантику и единицу измерения.

Внутреннее представление рекомендуется нормализовать к системе СИ.

| Величина | Обозначение | Единица СИ |
|---|---|---|
| Температура | T | K |
| Разность температур | ΔT | K |
| Тепловая мощность | P | W |
| Длина | L | m |
| Площадь | A | m² |
| Объём | V | m³ |
| Теплопроводность | λ | W/(m·K) |
| Тепловое сопротивление | Rθ | K/W |
| Коэффициент теплоотдачи | h | W/(m²·K) |
| Плотность | ρ | kg/m³ |
| Удельная теплоёмкость | cₚ | J/(kg·K) |
| Масса | m | kg |

Пользовательский интерфейс может отображать значения в более удобных единицах, например:

- °C вместо K;
- mm вместо m;
- W вместо kW;
- W/(m·K) для теплопроводности.

Преобразование единиц выполняется на границе ввода и отображения. Внутри расчётного ядра должны использоваться согласованные единицы.

### 4.2. Температура и разность температур

Температура и разность температур должны быть разными типами.

Это принципиально важно, поскольку преобразование абсолютной температуры между Celsius и Kelvin отличается от преобразования температурной разности.

Например:

\[
T_K = T_{^\circ C} + 273.15
\]

Для разности температур:

\[
\Delta T_K = \Delta T_{^\circ C}
\]

Предлагаемое представление:

```kotlin
@JvmInline
value class Temperature(
    val kelvin: Double
) {
    init {
        require(kelvin.isFinite())
        require(kelvin >= 0.0)
    }

    fun toCelsius(): Double = kelvin - 273.15

    companion object {
        fun fromCelsius(value: Double): Temperature {
            require(value.isFinite())
            return Temperature(value + 273.15)
        }
    }
}

@JvmInline
value class TemperatureDifference(
    val kelvin: Double
) {
    init {
        require(kelvin.isFinite())
    }
}
```

Необходимо избегать непосредственного сложения абсолютных температур и температурных разностей без явной семантики операции.

### 4.3. Другие физические величины

Пример реализации длины:

```kotlin
@JvmInline
value class Length(
    val meters: Double
) {
    init {
        require(meters.isFinite())
        require(meters >= 0.0)
    }

    fun toMillimeters(): Double = meters * 1000.0

    companion object {
        fun fromMillimeters(value: Double): Length {
            require(value.isFinite())
            return Length(value / 1000.0)
        }
    }
}
```

Пример мощности:

```kotlin
@JvmInline
value class Power(
    val watts: Double
) {
    init {
        require(watts.isFinite())
        require(watts >= 0.0)
    }
}
```

Пример теплопроводности:

```kotlin
@JvmInline
value class ThermalConductivity(
    val wattsPerMeterKelvin: Double
) {
    init {
        require(wattsPerMeterKelvin.isFinite())
        require(wattsPerMeterKelvin > 0.0)
    }
}
```

Пример теплового сопротивления:

```kotlin
@JvmInline
value class ThermalResistance(
    val kelvinPerWatt: Double
) {
    init {
        require(kelvinPerWatt.isFinite())
        require(kelvinPerWatt >= 0.0)
    }
}
```

Пример коэффициента теплоотдачи:

```kotlin
@JvmInline
value class HeatTransferCoefficient(
    val wattsPerSquareMeterKelvin: Double
) {
    init {
        require(wattsPerSquareMeterKelvin.isFinite())
        require(wattsPerSquareMeterKelvin > 0.0)
    }
}
```

Приведённые типы являются начальным набором. Остальные величины следует добавлять по мере появления конкретной потребности в расчётных моделях.

Важно: локальные ограничения конкретной модели не всегда совпадают с глобальными ограничениями физической величины. Например, отрицательное значение мощности в общем случае может описывать отвод энергии или иной знак теплового потока. Поэтому окончательные ограничения должны определяться семантикой конкретного параметра.

## 5. Геометрические характеристики

Геометрия описывает пространственные характеристики физических объектов.

### 5.1. Dimensions3D

```kotlin
data class Dimensions3D(
    val length: Length,
    val width: Length,
    val height: Length
) {
    init {
        require(length.meters > 0.0)
        require(width.meters > 0.0)
        require(height.meters > 0.0)
    }

    val volume: Volume
        get() = Volume(
            length.meters *
            width.meters *
            height.meters
        )
}
```

`Dimensions3D` представляет три геометрических размера, но не определяет автоматически способ расчёта эффективной площади теплообмена.

В реальной тепловой модели могут учитываться:

- внешняя поверхность корпуса;
- внутренняя поверхность;
- поверхность контакта;
- площадь оребрения;
- площадь перфорации;
- эффективная площадь теплообмена.

Эти значения должны рассчитываться с учётом конкретной геометрии и физических предпосылок модели.

### 5.2. Surface

```kotlin
@JvmInline
value class Area(
    val squareMeters: Double
) {
    init {
        require(squareMeters.isFinite())
        require(squareMeters >= 0.0)
    }
}
```

Площадь поверхности должна иметь явно определённый смысл. Нельзя использовать одно поле `area` для всех типов поверхностей без дополнительного контекста.

## 6. Материалы

Материал корпуса или другого элемента аппаратуры характеризуется физическими свойствами, влияющими на теплопередачу.

### 6.1. Material

```kotlin
data class Material(
    val id: String,
    val name: String,
    val thermalConductivity: ThermalConductivity,
    val density: Double? = null,
    val specificHeatCapacity: Double? = null
)
```

Основные характеристики:

- название материала;
- теплопроводность;
- плотность;
- удельная теплоёмкость.

Не все расчётные модели используют полный набор этих параметров.

Например, стационарная тепловая модель может не использовать теплоёмкость и плотность, тогда как переходная модель может требовать обе величины.

### 6.2. Температурная зависимость свойств

Физические свойства материала могут зависеть от температуры.

На первом этапе допустимо использовать постоянные значения, если это соответствует предпосылкам конкретной модели.

В дальнейшем можно добавить интерфейс:

```kotlin
interface TemperatureDependentProperty<T> {
    fun valueAt(temperature: Temperature): T
}
```

Такая абстракция нужна только при появлении моделей, действительно учитывающих изменение свойств с температурой.

Нельзя автоматически считать теплопроводность постоянной для всех материалов и температурных диапазонов.

## 7. Корпус радиоэлектронной аппаратуры

Корпус является одним из основных физических объектов Thermora.

### 7.1. Housing

```kotlin
data class Housing(
    val id: String,
    val name: String,
    val dimensions: Dimensions3D,
    val wallThickness: Length,
    val material: Material,
    val type: HousingType
)
```

### 7.2. HousingType

```kotlin
enum class HousingType {
    SEALED,
    FINNED,
    PERFORATED,
    VENTILATED
}
```

Тип корпуса характеризует его конструктивное исполнение.

Он не должен автоматически определять расчётную модель. Один и тот же корпус потенциально может использоваться в нескольких расчётных сценариях.

Например, герметичный корпус может анализироваться при естественном охлаждении и при дополнительных условиях внешнего обдува.

### 7.3. Конструктивные особенности

В зависимости от модели могут учитываться:

- толщина стенок;
- материал;
- площадь внешней поверхности;
- площадь внутренней поверхности;
- количество и геометрия рёбер;
- размеры и количество отверстий;
- параметры внутреннего пространства.

Не все характеристики должны присутствовать в базовом `Housing`.

Специфичные геометрические характеристики оребрения и перфорации следует добавлять отдельными структурами.

Пример:

```kotlin
data class FinGeometry(
    val count: Int,
    val height: Length,
    val thickness: Length,
    val spacing: Length
) {
    init {
        require(count > 0)
        require(height.meters > 0.0)
        require(thickness.meters > 0.0)
        require(spacing.meters > 0.0)
    }
}
```

Эта структура предназначена только для моделей, использующих геометрию оребрения.

## 8. Источники тепловыделения

### 8.1. HeatSource

Источник тепловыделения характеризует объект или группу объектов, выделяющих тепловую мощность.

```kotlin
data class HeatSource(
    val id: String,
    val name: String,
    val dissipatedPower: Power,
    val position: Position3D? = null
)
```

Положение источника может быть необходимо для моделей, учитывающих пространственное распределение тепловыделения.

Для упрощённых моделей, использующих суммарную мощность, оно может отсутствовать.

### 8.2. Position3D

```kotlin
data class Position3D(
    val x: Length,
    val y: Length,
    val z: Length
)
```

### 8.3. ElectronicComponent

```kotlin
data class ElectronicComponent(
    val id: String,
    val name: String,
    val heatSource: HeatSource,
    val maximumOperatingTemperature: Temperature? = null
)
```

Предметная модель должна различать:

- температуру окружающей среды;
- температуру корпуса электронного компонента;
- температуру перехода полупроводникового прибора;
- максимально допустимую температуру компонента.

Эти температуры не являются взаимозаменяемыми.

Если модель вычисляет температуру перехода через тепловое сопротивление «кристалл — корпус», соответствующие величины должны быть представлены явно.

## 9. Тепловая среда

Тепловая среда описывает внешние условия, в которых находится рассматриваемый объект.

### 9.1. ThermalEnvironment

```kotlin
data class ThermalEnvironment(
    val ambientTemperature: Temperature,
    val heatTransferCoefficient: HeatTransferCoefficient? = null
)
```

Температура окружающей среды является базовым параметром большинства тепловых моделей.

Коэффициент теплоотдачи может задаваться непосредственно или вычисляться отдельной моделью на основании условий охлаждения.

Нельзя считать его обязательным для всех сценариев.

### 9.2. CoolingConditions

Для сценариев принудительного охлаждения могут потребоваться дополнительные характеристики:

```kotlin
data class CoolingConditions(
    val airVelocity: Double? = null,
    val airTemperature: Temperature,
    val heatTransferCoefficient: HeatTransferCoefficient? = null
)
```

В окончательной реализации `airVelocity` следует заменить отдельным типом физической величины с единицей m/s.

В зависимости от модели могут потребоваться:

- скорость воздушного потока;
- направление движения воздуха;
- температура охлаждающей среды;
- свойства воздуха;
- геометрия канала;
- коэффициент теплоотдачи.

Эти характеристики не следует добавлять в базовый `ThermalEnvironment`, если они нужны только отдельным моделям.

## 10. Внутреннее перемешивание

Внутреннее перемешивание характеризует процессы переноса тепла внутри корпуса.

Для соответствующих моделей могут использоваться:

- геометрия внутреннего объёма;
- свойства внутренней среды;
- температурные характеристики;
- параметры циркуляции;
- коэффициенты внутреннего теплообмена.

Внутреннее перемешивание нельзя отождествлять с внешним обдувом корпуса.

Это разные физические процессы, имеющие разные граничные условия и расчётные зависимости.

Специфичные параметры должны находиться в отдельной структуре, например:

```kotlin
data class InternalMixingConditions(
    val fluidTemperature: Temperature,
    val characteristicLength: Length
)
```

Это пример возможного представления, а не окончательная спецификация Legacy-модели.

## 11. Происхождение исходных данных

Для инженерного расчёта важно знать не только значение параметра, но и откуда оно получено.

Одно и то же значение может быть:

- введено пользователем;
- получено из технической документации;
- импортировано из Excel;
- рассчитано другой моделью;
- принято как инженерное допущение.

### 11.1. ParameterSource

```kotlin
sealed interface ParameterSource {

    data object UserInput : ParameterSource

    data class TechnicalDocumentation(
        val documentName: String,
        val reference: String? = null
    ) : ParameterSource

    data class Imported(
        val sourceName: String,
        val sheet: String? = null,
        val cell: String? = null
    ) : ParameterSource

    data class Derived(
        val calculationId: String,
        val description: String
    ) : ParameterSource

    data class Assumption(
        val description: String
    ) : ParameterSource
}
```

### 11.2. ParameterValue

```kotlin
data class ParameterValue<T>(
    val value: T,
    val source: ParameterSource,
    val uncertainty: Double? = null
)
```

`ParameterValue` позволяет сохранять происхождение значения и дополнительную информацию о неопределённости.

Для величин, у которых неопределённость имеет физическую размерность, в дальнейшем следует использовать отдельное типизированное представление.

Важно не смешивать неопределённость измерения, допуск производства и численную погрешность алгоритма. Это разные понятия.

### 11.3. Почему происхождение данных важно

Например, теплопроводность материала может быть:

- взята из технического паспорта;
- импортирована из таблицы;
- принята как справочное значение;
- задана вручную.

При сравнении расчётов эта информация может существенно влиять на интерпретацию результата.

Поэтому происхождение параметров должно сохраняться вместе с исходными данными.

## 12. Расчётные сценарии и входные данные

Domain Model описывает физические понятия, но не должна создавать одну огромную структуру, содержащую параметры всех возможных расчётов.

Например, не следует создавать:

```kotlin
data class UniversalThermalInput(
    val housingLength: Double,
    val housingWidth: Double,
    val finCount: Int?,
    val holeCount: Int?,
    val airVelocity: Double?,
    val internalMixingCoefficient: Double?,
    val externalCoolingCoefficient: Double?
)
```

Подобная структура содержит множество необязательных полей, которые не имеют смысла для конкретных моделей.

Вместо этого следует формировать специализированные структуры.

Пример:

```kotlin
data class SealedHousingInput(
    val housing: Housing,
    val heatSources: List<HeatSource>,
    val environment: ThermalEnvironment
) : CalculationInput
```

Для модели внешнего охлаждения:

```kotlin
data class ExternalCoolingInput(
    val housing: Housing,
    val heatSources: List<HeatSource>,
    val environment: ThermalEnvironment,
    val coolingConditions: CoolingConditions
) : CalculationInput
```

Эти структуры являются примерами композиции предметных объектов. Окончательные поля должны определяться фактическими формулами и входными данными каждой модели.

При необходимости Legacy-модель может иметь собственный DTO, отличающийся от Improved-модели. Это допустимо, если различается смысл или набор необходимых параметров.

## 13. Результаты тепловых расчётов

Результаты должны представляться физическими величинами, а не форматированными строками.

### 13.1. TemperatureResult

```kotlin
data class TemperatureResult(
    val value: Temperature,
    val location: String? = null
)
```

Расположение позволяет различать температуры в разных точках объекта.

Например:

- температура внутреннего воздуха;
- температура внутренней поверхности корпуса;
- температура внешней поверхности корпуса;
- температура электронного компонента.

### 13.2. ThermalResult

```kotlin
data class ThermalResult(
    val temperatures: List<TemperatureResult>,
    val thermalResistance: ThermalResistance? = null
)
```

Это общий пример результата. Конкретные модели должны определять специализированные выходные структуры.

### 13.3. Результат и физическая допустимость

Необходимо сохранять различие между:

- численным результатом;
- физической интерпретацией;
- соответствием техническим ограничениям.

Например, вычисленная температура может быть математически корректной, но превышать максимально допустимую температуру компонента.

В таком случае результат расчёта сохраняется, а нарушение ограничения фиксируется отдельной диагностикой.

## 14. Физические ограничения и инварианты

Domain Model должна обеспечивать проверку базовых инвариантов.

Примеры:

| Параметр | Базовое ограничение |
|---|---|
| Абсолютная температура | T ≥ 0 K |
| Геометрическая длина | L ≥ 0 |
| Толщина стенки | L > 0 |
| Площадь | A ≥ 0 |
| Объём | V ≥ 0 |
| Теплопроводность | λ > 0 |
| Тепловая мощность | Ограничения определяются семантикой источника |
| Коэффициент теплоотдачи | h > 0, если он задан как положительный коэффициент |
| Количество рёбер | N > 0 |

Необходимо разделять два уровня ограничений.

**Общие ограничения предметной области** проверяются при создании соответствующих типов и объектов.

**Ограничения конкретной модели** проверяются при валидации входных данных.

Например, положительная толщина стенки является общим требованием для физического корпуса. А минимальная толщина, допустимая для конкретной эмпирической формулы, является ограничением применимости конкретной модели.

Не следует размещать все проверки в конструкторах объектов: некоторые условия зависят от комбинации параметров и известны только на уровне расчётного сценария.

## 15. Связь Domain Model с Calculation API

Domain Model и Calculation API выполняют разные задачи.

| Domain Model | Calculation API |
|---|---|
| Описывает физические величины | Определяет контракт расчётной модели |
| Описывает корпус и материалы | Определяет тип входных данных модели |
| Описывает источники тепла | Определяет способ передачи входных данных |
| Определяет единицы измерения | Определяет формат результата выполнения |
| Содержит физические инварианты | Содержит диагностику и статус выполнения |

Расчётная модель использует предметные типы в своих входных и выходных структурах.

Например:

```kotlin
data class SealedHousingInput(
    val housing: Housing,
    val heatSources: List<HeatSource>,
    val environment: ThermalEnvironment
) : CalculationInput
```

Таким образом, Calculation API не должен дублировать физические определения, уже существующие в Domain Model.

При этом общие типы выполнения, диагностики и метаданных не должны переноситься в предметную модель без необходимости.

## 16. Связь с Excel

Исходная Excel-модель является источником Legacy-логики, но не должна определять архитектуру Domain Model целиком.

Excel содержит расчётные листы:

- «Исходные данные»;
- «Герметичный корпус»;
- «Внутреннее перемешивание»;
- «Нарудный обдув»;
- «Оребрение герметичного корпуса»;
- «Перфорированный корпус»;
- «Продуваемый корпус».

Названия листов могут использоваться для сопоставления исходных расчётных сценариев, но не должны напрямую становиться именами предметных сущностей.

Для переноса Excel в Thermora необходимо составить таблицу соответствия:

| Excel | Domain Model | Calculation Model |
|---|---|---|
| Исходные данные | Общие физические параметры | Зависит от сценария |
| Герметичный корпус | Корпус, материал, тепловая среда | Sealed Housing |
| Внутреннее перемешивание | Внутренние условия теплообмена | Internal Mixing |
| Нарудный обдув | Условия внешнего охлаждения | External Cooling |
| Оребрение герметичного корпуса | Геометрия оребрения | Finned Housing |
| Перфорированный корпус | Геометрия перфорации | Perforated Housing |
| Продуваемый корпус | Геометрия и условия принудительного охлаждения | Forced Cooling |

Эта таблица является предварительным концептуальным сопоставлением. Она не заменяет анализ конкретных ячеек, формул и зависимостей исходного Excel.

При переносе необходимо сохранить:

- исходное название параметра;
- адрес ячейки;
- исходную единицу измерения;
- преобразование единиц, если оно требуется;
- формулу или источник значения;
- связь с конкретной Legacy-моделью.

Неизвестные формулы и эмпирические коэффициенты должны быть помечены как требующие проверки.

## 17. Сериализация и хранение

Domain Model не должна зависеть от конкретной технологии хранения.

Однако структуры данных должны допускать сохранение и восстановление.

Для этого рекомендуется использовать отдельные сериализуемые DTO, если доменные типы содержат сложные или нестандартные представления.

Например:

```text
Domain Model
     |
     v
Persistence DTO
     |
     v
Serialization
     |
     v
Database / File
```

В сохранённом расчёте должны присутствовать:

- исходные параметры;
- единицы измерения или зафиксированная схема единиц;
- происхождение исходных значений;
- идентификатор модели;
- версия модели;
- версия алгоритма;
- результат;
- диагностические сообщения;
- дата выполнения.

Изменение структуры Domain Model не должно приводить к невозможности прочитать старые расчёты.

Для этого необходимо версионировать схемы сохранения и при необходимости реализовывать миграции.

## 18. Тестирование Domain Model

Для предметной модели необходимы отдельные тесты.

### 18.1. Тесты физических величин

Проверяются:

- преобразование Celsius в Kelvin;
- преобразование миллиметров в метры;
- корректность представления разности температур;
- отклонение недопустимых значений;
- обработка `NaN` и бесконечности.

### 18.2. Тесты геометрии

Проверяются:

- положительность основных размеров;
- корректность вычисления объёма;
- корректность вычисления площади, если она реализована;
- обработка нулевых и отрицательных размеров.

### 18.3. Тесты предметных инвариантов

Проверяются:

- согласованность характеристик корпуса;
- допустимость характеристик материала;
- корректность параметров источников тепла;
- ограничения конкретных физических объектов.

### 18.4. Тесты сериализации

Проверяются:

- сохранение и восстановление физических величин;
- сохранение единиц измерения;
- сохранение происхождения параметров;
- совместимость версий схемы.

## 19. Этапы реализации

### Этап 1. Базовые физические величины

Реализовать:

- Temperature;
- TemperatureDifference;
- Power;
- Length;
- Area;
- Volume;
- ThermalConductivity;
- ThermalResistance;
- HeatTransferCoefficient.

На этом этапе не нужно реализовывать полный набор физических единиц.

### Этап 2. Базовые предметные объекты

Реализовать:

- Dimensions3D;
- Material;
- Housing;
- HeatSource;
- ThermalEnvironment.

### Этап 3. Происхождение исходных данных

Добавить:

- ParameterSource;
- ParameterValue;
- фиксацию единиц измерения;
- информацию об источниках данных.

### Этап 4. Специализированные структуры

Добавлять структуры для:

- внутреннего перемешивания;
- внешнего охлаждения;
- оребрения;
- перфорации;
- продуваемых корпусов.

Каждая структура должна появляться только при наличии конкретного сценария использования.

### Этап 5. Интеграция с Legacy

На примере одной модели:

1. Сопоставить входные параметры Excel с доменными величинами.
2. Определить единицы измерения.
3. Реализовать преобразование исходных данных.
4. Проверить физические ограничения.
5. Реализовать расчётную модель.
6. Сравнить результат с Excel.
7. Зафиксировать расхождения.

## 20. Принятые архитектурные ограничения

На первоначальном этапе не предусматриваются:

- универсальная система описания любых физических объектов;
- полноценная CAD-модель геометрии;
- трёхмерная сетка конечных элементов;
- универсальный граф тепловых связей;
- автоматическое получение физических свойств материалов из внешних баз;
- универсальная система неопределённости измерений;
- динамические физические свойства для всех материалов;
- обязательное использование всех параметров во всех расчётных моделях.

Эти функции могут быть добавлены при расширении Thermora, но не должны усложнять базовую предметную модель.

## 21. Открытые вопросы

Перед окончательной фиксацией Domain Model необходимо определить:

1. Полный перечень параметров исходной Excel-модели с адресами ячеек и единицами измерения.
2. Какие параметры являются общими для нескольких расчётных моделей.
3. Какие физические величины должны быть представлены отдельными типами уже в первой версии.
4. Какие материалы и их характеристики должны поддерживаться.
5. Какие результаты должны быть доступны для сравнения Legacy и Improved.
6. Какие физические ограничения можно проверять автоматически.
7. Нужна ли поддержка переходных тепловых процессов или первоначальная версия ограничивается стационарными расчётами.

До анализа всех формул Excel нельзя считать предложенные структуры окончательной спецификацией конкретных расчётных моделей.

---

## Итог

Domain Model определяет единый физический язык Thermora.

Она отделяет физические объекты, величины и характеристики от конкретных расчётных алгоритмов. Благодаря этому Legacy и Improved модели могут использовать общие предметные понятия, не будучи вынужденными применять одинаковые формулы или одинаковые наборы входных параметров.

Главный принцип: **предметная модель описывает физическую реальность, а расчётная модель определяет, как конкретные физические явления будут математически описаны и вычислены.**
