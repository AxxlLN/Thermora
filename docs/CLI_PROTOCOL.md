# Thermora — CLI Protocol V1

**Версия документа:** 1.0  
**Статус:** Draft  
**Версия протокола:** 1  
**Целевая версия CLI:** 1.0.0  
**Базовая версия Core:** 1.0.0  
**Платформа:** Kotlin/JVM, JDK 21  
**Транспорт:** Standard Input / Standard Output  
**Формат данных:** JSON  
**Кодировка:** UTF-8

---

## 1. Назначение

Thermora CLI — независимый интерфейс взаимодействия с вычислительным ядром Thermora, предназначенный для выполнения инженерных расчётов из внешних приложений и командной строки.

CLI обеспечивает:

- получение списка доступных расчётных моделей;
- получение метаданных расчётной модели;
- получение схем входных и выходных данных;
- валидацию входных параметров;
- выполнение тепловых расчётов;
- сериализацию результатов;
- передачу диагностических сообщений;
- автоматизированное взаимодействие с внешними приложениями.

Основным программным потребителем CLI является Thermora Desktop, реализуемый на C++20 с использованием Qt 6.

CLI должен поддерживать полностью автономную работу без подключения к сети и без использования удалённого сервера.

---

## 2. Архитектурные принципы

CLI является входным адаптером вычислительного ядра Thermora.

Основные принципы:

1. Независимость вычислительного ядра от CLI.
2. Отсутствие физических формул в CLI.
3. Повторное использование существующих расчётных моделей.
4. Повторное использование существующих механизмов сериализации.
5. Строгая типизация внутренних контрактов.
6. Независимое версионирование протокола.
7. Детерминированная структура сообщений.
8. Явная обработка ошибок.
9. Ограниченное потребление ресурсов.
10. Независимость от конкретного внешнего клиента.
11. Отсутствие обязательных сетевых зависимостей.
12. Возможность последующей нативной компиляции.

CLI не должен обращаться непосредственно к внутренним компонентам Calculation Engine.

Взаимодействие с вычислительным ядром осуществляется через публичный API Application Core и зарегистрированные привязки моделей.

## 4. Область действия протокола

CLI Protocol V1 определяет:

- синтаксис команд;
- транспорт сообщений;
- структуру запросов;
- структуру ответов;
- идентификацию расчётных моделей;
- идентификацию схем сериализации;
- передачу диагностических сообщений;
- классификацию ошибок;
- коды завершения процесса;
- ограничения ресурсов;
- правила совместимости.

Протокол не определяет:

- физические формулы;
- математические методы расчёта;
- внутреннюю структуру Calculation Engine;
- формат хранения проектов `.thra`;
- пользовательский интерфейс;
- сетевые API;
- механизмы лицензирования;
- механизмы защиты исполняемых файлов.

## 5. Версионирование

В Thermora используются независимые уровни версионирования.

| Компонент | Тип версии | Пример |
|---|---|---|
| Thermora Core | Semantic Versioning | 1.0.0 |
| Thermora CLI | Semantic Versioning | 1.0.0 |
| CLI Protocol | Положительное целое число | 1 |
| Calculation Model | Строковый идентификатор версии | 1.0.0 |
| Snapshot Schema | Положительное целое число | 1 |
| Project Format | Независимая версия | 1 |

### 5.1. Версия протокола

Каждый машинный запрос содержит поле:

```json
{
  "protocolVersion": 1
}
```

CLI обязан проверять поддерживаемую версию протокола до выполнения прикладной операции.

Неподдерживаемая версия должна приводить к ошибке:

```text
UNSUPPORTED_PROTOCOL_VERSION
```

Автоматический переход на другую версию протокола запрещён.

### 5.2. Версия модели

Версия модели определяется её дескриптором.

При выполнении расчёта клиент должен явно указать требуемую версию модели.

CLI Protocol V1 использует точное строковое сравнение версий моделей.

Автоматический выбор другой версии модели запрещён.

### 5.3. Версия схемы

Схема сериализации определяется парой:

```text
Schema ID + Schema Version
```

Версия схемы не зависит от версии CLI-протокола.

Автоматическая миграция модельных данных между версиями схем не выполняется.

## 6. Режимы выполнения

### 6.1. Одноразовый процесс

Основной режим CLI Protocol V1.

Жизненный цикл:

```text
Start Process
    │
    ▼
Parse Command
    │
    ▼
Read Request
    │
    ▼
Validate Protocol
    │
    ▼
Execute Operation
    │
    ▼
Write Response
    │
    ▼
Exit Process
```

Один процесс обслуживает не более одной прикладной операции.

Для команд, принимающих JSON-запрос, входной поток читается до EOF с соблюдением установленного ограничения размера.

После формирования ответа процесс завершается.

### 6.2. Постоянный процесс

Постоянный процесс предназначен для уменьшения накладных расходов на запуск JVM при многократном выполнении расчётов.

Предполагаемая команда:

```bash
thermora serve-stdio
```

Предполагаемый формат обмена — NDJSON.

Реализация постоянного процесса не является обязательным условием готовности одноразового режима.

До утверждения отдельной спецификации постоянного процесса команда не считается поддерживаемой частью CLI Protocol V1.

## 7. Стандартные потоки

### 7.1. Standard Input

`stdin` используется для получения JSON-запросов.

Команды `validate` и `calculate` принимают один JSON-документ через стандартный входной поток.

Интерактивные запросы данных и ожидание пользовательского ввода после получения документа запрещены.

### 7.2. Standard Output

`stdout` используется для передачи результата команды.

В машинном режиме разрешается вывод ровно одного JSON-документа.

После JSON-документа допускается один символ LF.

Запрещается выводить в stdout машинного режима:

- приветственные сообщения;
- отладочные сообщения;
- технические логи;
- индикаторы прогресса;
- stack traces;
- текстовую справку;
- дополнительные JSON-документы.

Команда `help` является исключением и использует человекочитаемый текстовый формат.

### 7.3. Standard Error

`stderr` предназначен для технических сообщений:

- ошибок аргументов командной строки;
- ошибок запуска;
- внутренних диагностических сообщений;
- технических логов;
- информации об аварийном завершении.

Клиент не должен использовать stderr в качестве источника результатов расчёта.

Диагностика, относящаяся к результату прикладной операции, должна передаваться в JSON-ответе.

---

## 8. Кодировка и формат JSON

Все машинные сообщения используют UTF-8.

Обязательные требования:

- корректная последовательность UTF-8;
- отсутствие Byte Order Mark;
- один корневой JSON-объект;
- отсутствие повторяющихся ключей;
- отсутствие комментариев;
- отсутствие trailing commas;
- отсутствие дополнительных корневых значений;
- отсутствие непарных Unicode surrogate;
- соответствие JSON-грамматике.

Декодирование входных байтов должно выполняться с использованием строгой политики обработки ошибок.

Замена некорректных последовательностей символом U+FFFD запрещена.

Порядок полей входного JSON-объекта не имеет значения.

Порядок полей выходного JSON-объекта должен быть детерминированным, но не является частью семантического контракта.

Клиент не должен зависеть от порядка ключей.

## 13. Команда describe-model

### 13.1. Синтаксис

```bash
thermora describe-model <model-id>
```

Получение JSON Schema:

```bash
thermora describe-model <model-id> --schema input
thermora describe-model <model-id> --schema output
```

### 13.2. Назначение

Получение:

- идентификатора модели;
- имени модели;
- версии модели;
- описания модели;
- идентификатора входной схемы;
- версии входной схемы;
- идентификатора выходной схемы;
- версии выходной схемы.

### 13.3. Пример ответа

```json
{
  "protocolVersion": 1,
  "requestId": null,
  "status": "success",
  "data": {
    "model": {
      "id": "sealed-housing-legacy",
      "name": "Sealed Housing",
      "version": "1.0.0",
      "description": null
    },
    "inputSchema": {
      "id": "thermora.sealed-housing.legacy.input",
      "version": 1
    },
    "outputSchema": {
      "id": "thermora.sealed-housing.legacy.output",
      "version": 1
    }
  },
  "diagnostics": []
}
```

### 13.4. Получение схемы

При использовании параметра `--schema` поле `data` содержит:

- `modelId`;
- `modelVersion`;
- `direction`;
- `schemaId`;
- `schemaVersion`;
- `schema` — документ JSON Schema.

Допустимые значения `direction`:

- `input`;
- `output`.

Схемы используют JSON Schema Draft 2020-12.

JSON Schema должны поставляться как runtime-ресурсы.

Дублирование независимых копий одной схемы в production и test resources запрещено.

### 13.5. Ограничения

JSON Schema описывает структуру сериализованных данных, но не заменяет физическую валидацию.

Метаданные для автоматической генерации пользовательских форм, единиц отображения, значений по умолчанию и допустимых инженерных диапазонов не входят в обязательный контракт V1.

## 14. Общая структура расчётного запроса

Команды `validate` и `calculate` используют одинаковую структуру входного запроса.

```json
{
  "protocolVersion": 1,
  "requestId": "request-001",
  "modelId": "sealed-housing-legacy",
  "modelVersion": "1.0.0",
  "input": {
    "schemaId": "thermora.sealed-housing.legacy.input",
    "schemaVersion": 1,
    "payload": {}
  }
}
```

Пустой объект `payload` приведён исключительно для демонстрации структуры сообщения и не является корректным входом физической модели.

### 14.1. Поля запроса

| Поле | Тип | Обязательное |
|---|---|---|
| protocolVersion | Integer | Да |
| requestId | String | Да |
| modelId | String | Да |
| modelVersion | String | Да |
| input | Object | Да |
| input.schemaId | String | Да |
| input.schemaVersion | Integer | Да |
| input.payload | Object | Да |

Неизвестные поля внешнего запроса запрещены.

Все обязательные поля должны присутствовать.

Явное значение null для обязательных полей запрещено.

### 14.2. Request ID

`requestId` используется для сопоставления запроса и ответа.

Требования:

- длина от 1 до 128 символов;
- допустимые символы: латинские буквы, цифры, точка, дефис, подчёркивание;
- чувствительность к регистру.

Допускается использование UUID.

CLI не интерпретирует содержимое идентификатора и не изменяет его.

В одноразовом режиме CLI не обеспечивает глобальную уникальность идентификаторов.

Ответственность за уникальность идентификаторов между запросами несёт клиент.

### 14.3. Model ID

Идентификатор модели должен соответствовать существующему контракту CalculationModelId:

```text
[a-z0-9][a-z0-9._-]*
```

Идентификатор не должен преобразовываться или нормализоваться.

### 14.4. Payload

Поле `payload` содержит модельный JSON-объект.

Структура определяется указанной схемой сериализации.

CLI не должен самостоятельно интерпретировать физический смысл полей payload.

Проверка модельных данных выполняется соответствующим SnapshotCodec и расчётной моделью.

---

## 15. Сохранение модельного JSON

Модельный payload должен передаваться существующему SnapshotCodec без потери информации, необходимой для строгой проверки.

Запрещается:

- преобразовывать payload в нетипизированный Map с последующей сериализацией;
- устранять повторяющиеся ключи;
- преобразовывать числовые токены до передачи кодеку;
- автоматически исправлять некорректные значения;
- нормализовывать signed zero;
- заменять неизвестные поля;
- добавлять отсутствующие поля;
- преобразовывать единицы измерения.

Предпочтительный механизм — извлечение исходного JSON-поддерева с сохранением его лексического представления.

Проверка внешнего envelope и проверка модельного payload должны оставаться отдельными операциями.

Техническая реализация должна подтверждаться тестами на:

- duplicate fields;
- signed zero;
- subnormal numbers;
- числовое переполнение;
- ненулевые значения, округляющиеся до нуля;
- некорректные Unicode escape;
- превышение ограничений ресурсов.

## 16. Команда validate

### 16.1. Синтаксис

```bash
thermora validate < input.json
```

### 16.2. Назначение

Проверка входных параметров без выполнения физического расчёта.

### 16.3. Последовательность выполнения

```text
Read Request
    │
    ▼
Validate Envelope
    │
    ▼
Resolve Model Binding
    │
    ▼
Verify Model Version
    │
    ▼
Verify Input Schema
    │
    ▼
Decode Input
    │
    ▼
Model.validate(input)
    │
    ▼
Build Response
```

### 16.4. Успешная валидация

```json
{
  "protocolVersion": 1,
  "requestId": "request-001",
  "status": "success",
  "data": {
    "modelId": "sealed-housing-legacy",
    "modelVersion": "1.0.0",
    "isValid": true,
    "hasWarnings": false
  },
  "diagnostics": []
}
```

### 16.5. Отрицательный результат валидации

```json
{
  "protocolVersion": 1,
  "requestId": "request-001",
  "status": "success",
  "data": {
    "modelId": "sealed-housing-legacy",
    "modelVersion": "1.0.0",
    "isValid": false,
    "hasWarnings": false
  },
  "diagnostics": [
    {
      "code": "NOT_POSITIVE_NUMBER",
      "message": "Value must be positive",
      "severity": "error",
      "source": null,
      "details": {}
    }
  ]
}
```

В данном случае команда успешно выполнила операцию проверки, но входные параметры не прошли физическую валидацию.

Поэтому:

- статус выполнения команды — `success`;
- результат валидации — `isValid: false`;
- код завершения процесса — `0`.

Если входной payload невозможно декодировать, команда возвращает `failure`, поскольку модельная валидация не была выполнена.

### 16.6. Ограничения

Команда validate не должна:

- выполнять CalculationModel.calculate;
- создавать историю расчётов;
- формировать расчётный Output;
- изменять входные параметры;
- автоматически исправлять физически некорректные данные.

---

## 17. Команда calculate

### 17.1. Синтаксис

```bash
thermora calculate < input.json
```

### 17.2. Назначение

Выполнение зарегистрированной расчётной модели и получение сериализованного результата.

### 17.3. Последовательность выполнения

```text
Read Request
    │
    ▼
Validate Envelope
    │
    ▼
Resolve Model Binding
    │
    ▼
Verify Model Version
    │
    ▼
Verify Input Schema
    │
    ▼
Decode Input
    │
    ▼
ThermoraCore.calculate(...)
    │
    ├── Failure ──► Error Response
    │
    ▼
Encode Output
    │
    ▼
Success Response
```

Модельная валидация выполняется существующим Calculation Engine.

CLI не должен повторно вызывать модельную валидацию перед штатным вызовом Core.calculate.

### 17.4. Успешный ответ

```json
{
  "protocolVersion": 1,
  "requestId": "request-001",
  "status": "success",
  "data": {
    "modelId": "sealed-housing-legacy",
    "modelVersion": "1.0.0",
    "output": {
      "schemaId": "thermora.sealed-housing.legacy.output",
      "schemaVersion": 1,
      "payload": {}
    }
  },
  "diagnostics": []
}
```

Пустой output payload является условным примером.

Фактический результат должен соответствовать выходной схеме модели.

### 17.5. Расчёт с предупреждениями

Если Core возвращает CalculationResult.Success с диагностическими сообщениями уровня WARNING, CLI сохраняет успешный статус.

Предупреждения передаются без изменения их семантики.

В частности, несошедшийся шаг Legacy-модели может оставаться успешным расчётом, если такое поведение предусмотрено моделью.

### 17.6. Ошибка расчёта

```json
{
  "protocolVersion": 1,
  "requestId": "request-001",
  "status": "failure",
  "error": {
    "stage": "calculation",
    "code": "CALCULATION_FAILED",
    "message": "Calculation could not be completed"
  },
  "diagnostics": []
}
```

Фактические диагностические сообщения Core должны сохраняться в массиве diagnostics.

## 18. Общая структура ответа

### 18.1. Успешный ответ

```json
{
  "protocolVersion": 1,
  "requestId": "request-001",
  "status": "success",
  "data": {},
  "diagnostics": []
}
```

### 18.2. Неуспешный ответ

```json
{
  "protocolVersion": 1,
  "requestId": "request-001",
  "status": "failure",
  "error": {
    "stage": "dispatch",
    "code": "MODEL_NOT_FOUND",
    "message": "Requested model is not registered"
  },
  "diagnostics": []
}
```

### 18.3. Правила

- `protocolVersion` присутствует всегда.
- `requestId` присутствует всегда.
- `status` присутствует всегда.
- `diagnostics` присутствует всегда.
- `data` присутствует только при success.
- `error` присутствует только при failure.
- Одновременное присутствие data и error запрещено.
- Неизвестные поля ответа V1 не допускаются.

Допустимые значения status:

```text
success
failure
```

Если команда не принимает JSON-запрос, requestId равен null.

Если входной запрос повреждён и идентификатор невозможно достоверно определить, requestId равен null.

## 19. Диагностические сообщения

CLI переиспользует семантику foundation:common.

### 19.1. Структура

```json
{
  "code": "DIAGNOSTIC_CODE",
  "message": "Human-readable diagnostic message",
  "severity": "warning",
  "source": null,
  "details": {}
}
```

### 19.2. Поля

| Поле | Тип | Nullable |
|---|---|---|
| code | String | Нет |
| message | String | Нет |
| severity | String | Нет |
| source | String | Да |
| details | Object<String, String> | Нет |

Все пять полей присутствуют в каждом диагностическом сообщении.

### 19.3. Уровни серьёзности

| Foundation | Protocol |
|---|---|
| INFO | info |
| WARNING | warning |
| ERROR | error |

Преобразование выполняется явно.

Порядковые номера enum не используются в wire-формате.

### 19.4. Сохранение диагностики

CLI должен сохранять:

- исходный диагностический код;
- исходное сообщение;
- уровень серьёзности;
- источник;
- дополнительные данные;
- порядок диагностических сообщений.

Диагностика не должна молча удаляться или заменяться обобщёнными сообщениями.

Структурированный JSON-path ошибок сериализации не входит в обязательный контракт V1, поскольку существующий SnapshotCodecResult.Failure предоставляет код и текст сообщения.

## 20. Стадии ошибок

Каждая протокольная ошибка содержит стадию возникновения.

| Stage | Назначение |
|---|---|
| command | Обработка аргументов |
| transport | Чтение и декодирование входного потока |
| protocol | Проверка JSON envelope |
| dispatch | Поиск модели и проверка версий |
| input | Декодирование модельных данных |
| validation | Выполнение отдельной операции валидации |
| calculation | Выполнение расчёта |
| output | Сериализация результата |
| internal | Внутренняя ошибка приложения |

Стадия отражает место возникновения ошибки, а не уровень серьёзности диагностики.

## 22. Преобразование ошибок SnapshotCodec

| SnapshotCodecError | CLI Error Code при декодировании |
|---|---|
| SCHEMA_MISMATCH | INPUT_SCHEMA_MISMATCH |
| UNSUPPORTED_SCHEMA | UNSUPPORTED_INPUT_SCHEMA |
| INVALID_PAYLOAD | INVALID_INPUT_PAYLOAD |
| INVALID_VALUE | INVALID_INPUT_VALUE |
| INTERNAL_ERROR | INPUT_DECODING_FAILED |

Ошибка выходного кодека преобразуется в OUTPUT_ENCODING_FAILED независимо от конкретного значения SnapshotCodecError.

Если физический расчёт был успешно выполнен, но его результат невозможно сериализовать, итоговый ответ CLI считается неуспешным.

Ранее полученная диагностика расчёта должна сохраняться, если её возможно представить в пределах ограничений протокола.

## 23. Коды завершения процесса

| Exit Code | Назначение |
|---:|---|
| 0 | Операция успешно выполнена |
| 2 | Некорректная команда, запрос или входные данные |
| 3 | Расчётная модель вернула Failure |
| 4 | Внутренняя ошибка CLI |

### 23.1. Код 0

Используется для:

- успешного выполнения help;
- успешного получения версии;
- успешного получения списка моделей;
- успешного получения описания модели;
- выполненной операции validate, включая isValid=false;
- успешного расчёта;
- успешного расчёта с предупреждениями.

### 23.2. Код 2

Используется для:

- неизвестных команд;
- некорректных аргументов;
- повреждённого UTF-8;
- некорректного JSON;
- неподдерживаемой версии протокола;
- неизвестной модели;
- несовместимой версии модели;
- несовместимой входной схемы;
- некорректного модельного payload;
- превышения входных ограничений.

### 23.3. Код 3

Используется, если Core вернул CalculationResult.Failure, за исключением диагностик, однозначно указывающих на нарушение внутреннего контракта выполнения.

### 23.4. Код 4

Используется для:

- ошибок конфигурации;
- внутренних ошибок чтения;
- внутренних ошибок декодирования;
- ошибок выполнения операции validate;
- внутренних нарушений контракта Core;
- ошибок сериализации результата;
- превышения выходных ограничений;
- непредвиденных исключений.

### 23.5. Аварийное завершение

Завершение процесса операционной системой, принудительная остановка и невозможность запуска не являются штатными кодами CLI-протокола.

Клиент должен обрабатывать такие ситуации отдельно.

## 24. Каталог привязок моделей

CLI использует типизированные привязки моделей.

Концептуальный контракт:

```kotlin
class ModelBinding<
    I : CalculationInput,
    O : CalculationOutput
>(
    val model: CalculationModel<I, O>,
    val inputCodec: SnapshotCodec<I>,
    val outputCodec: SnapshotCodec<O>
)
```

Привязка содержит:

- экземпляр расчётной модели;
- дескриптор модели;
- тип входных данных;
- тип выходных данных;
- входной кодек;
- выходной кодек;
- входную схему;
- выходную схему.

### 24.1. Model Binding Registry

Реестр обеспечивает:

- регистрацию привязок;
- поиск по Model ID;
- получение списка доступных моделей;
- проверку уникальности идентификаторов;
- проверку совместимости типов;
- проверку конфигурации.

Реестр после создания должен быть неизменяемым.

### 24.2. Проверка совместимости

При создании привязки необходимо проверить:

```text
model.inputType == inputCodec.valueType
model.outputType == outputCodec.valueType
```

Несовместимая привязка является ошибкой конфигурации.

### 24.3. Инициализация Core

Экземпляр ThermoraCore должен создаваться из тех же экземпляров моделей, которые используются в Model Binding Registry.

Концептуально:

```text
Model Bindings
    │
    ├── Model Binding Registry
    │
    └── ThermoraCoreFactory.create(models)
```

Это обеспечивает согласованность операций validate и calculate.

### 24.4. Расширяемость

Добавление новой модели требует:

1. Реализации CalculationModel.
2. Реализации входного и выходного кодеков.
3. Определения схем сериализации.
4. Регистрации ModelBinding.

Изменение универсальных обработчиков validate и calculate не требуется.

Автоматическое связывание по имени Kotlin-класса или строковым преобразованиям идентификаторов схем запрещено.

## 25. Ограничения ресурсов

CLI должен применять ограничения до выполнения потенциально дорогостоящих операций.

### 25.1. Ограничения внешнего протокола

| Параметр | Максимум |
|---|---:|
| Размер входного сообщения | 2 MiB |
| Размер выходного сообщения | 2 MiB |
| Глубина вложенности envelope вместе с payload | 40 |
| Длина requestId | 128 ASCII-символов |
| Длина modelId | 128 ASCII-символов |
| Длина modelVersion | 128 единиц UTF-16 |
| Длина schemaId | 256 единиц UTF-16 |
| Количество диагностических сообщений | 256 |
| Количество полей details одного сообщения | 256 |
| Длина диагностического сообщения | 8192 единицы UTF-16 |

Один MiB равен 1 048 576 байтам.

Ограничение размера применяется ко всему сообщению, включая служебные поля и завершающие пробельные символы.

### 25.2. Ограничения модельного payload

Сохраняются существующие ограничения SnapshotCodec.

| Параметр | Максимум |
|---|---:|
| Размер JSON | 1 MiB |
| Глубина вложенности | 32 |
| Элементов одного массива | 256 |
| Длина числового токена | 64 |
| Длина имени JSON-поля | 256 единиц UTF-16 |
| Длина строкового значения | 256 единиц UTF-16 |

Ограничения envelope не должны ослаблять ограничения модельного payload.

### 25.3. Обработка превышений

При превышении входных ограничений запрос отклоняется.

При превышении выходных ограничений CLI должен сформировать ограниченный по размеру ответ с ошибкой RESPONSE_TOO_LARGE, если stdout ещё не был повреждён частичной записью.

Полный ответ должен быть сформирован и проверен до начала записи в stdout.

Молчаливое усечение модельных данных и диагностических сообщений запрещено.

При невозможности сформировать даже минимальный корректный ответ процесс завершается с кодом `4`.

```json
  }
```

### 26.2. Temperature

```json
{
  "kelvin": 313.15
```

### 26.3. TemperatureDelta

### 26.4. ThermalResistance

```json
    "kind": "standard",
```

- запрет Infinity;

## 27. Обработка исключений

CLI должен различать:

- ожидаемые ошибки пользовательского ввода;
- ошибки протокола;
- ошибки конфигурации;
- ошибки вычислительного ядра;
- программные дефекты;
- аварийное завершение процесса.

Ожидаемые ошибки должны преобразовываться в структурированные ответы.

Не допускается преобразование всех исключений в ошибку пользовательского ввода.

CancellationException не должна интерпретироваться как ошибка валидации.

При InterruptedException необходимо сохранять interrupt flag.

JVM Error не должен маскироваться обычной обработкой прикладных ошибок.

Stack traces не должны включаться в JSON-ответ.

Техническая информация может передаваться через stderr.

## 28. Интеграция с Qt Desktop

Qt Desktop взаимодействует с CLI посредством QProcess.

### 28.1. Запуск процесса

Исполняемый файл запускается напрямую.

Использование shell-интерпретации аргументов запрещено.

Аргументы передаются отдельным списком.

### 28.2. Последовательность взаимодействия

```text
Qt Desktop
    │
    ├── QProcess.start()
    │
    ├── QProcess.write(request)
    │
    ├── QProcess.closeWriteChannel()
    │
    ├── Read stdout asynchronously
    │
    ├── Read stderr asynchronously
    │
    ├── Process finished
    │
    ├── Verify exit status
    │
    ├── Parse JSON response
    │
    ├── Verify protocol version
    │
    └── Verify request ID
```

### 28.3. Асинхронность

Выполнение CLI не должно блокировать GUI thread.

Qt Desktop должен отдельно обрабатывать:

- ошибку запуска;
- штатное завершение;
- аварийное завершение;
- превышение времени ожидания;
- принудительную остановку;
- повреждённый ответ;
- несовместимую версию протокола;
- несовпадающий requestId;
- превышение размера выходного потока.

### 28.4. Проверка согласованности

Клиент должен проверять согласованность JSON-статуса и кода завершения процесса.

Успешный JSON-ответ при ненулевом штатном exit code является нарушением протокола.

Неуспешный JSON-ответ при exit code 0 также является нарушением протокола.

Отрицательный результат операции validate представлен успешным ответом и не нарушает данное правило.

## 29. Таймауты и отмена

CLI Protocol V1 в одноразовом режиме не предоставляет кооперативную отмену отдельных расчётов.

Управление временем ожидания осуществляется внешним клиентом.

При превышении времени ожидания клиент может:

1. Запросить завершение процесса.
2. Предоставить ограниченное время на остановку.
3. Принудительно завершить процесс.

Принудительная остановка процесса не гарантирует получение корректного JSON-ответа.

Результат остановленного процесса не должен использоваться как завершённый расчёт.

Параметры deadline, progress callback и cancellation token не входят в обязательный контракт V1.

## 30. Хранение состояния

Одноразовый CLI является stateless-приложением на уровне внешних запросов.

CLI не должен автоматически:

- создавать файлы проектов;
- сохранять историю расчётов;
- создавать CalculationRecord;
- генерировать постоянные идентификаторы расчётов;
- записывать пользовательские данные в базу данных;
- сохранять состояние между запусками.

Существующие SnapshotCodec используются для сериализации, а не для обязательного сохранения истории.

Постоянное хранение проектов будет реализовано отдельным архитектурным этапом.

## 31. Gradle-зависимости

Минимальный граф зависимостей CLI:

```text
interfaces:cli
│
├── application:core
│   ├── calculation:api
│   ├── application:ports
│   ├── foundation:common
│   ├── calculation:engine
│   └── models:*
│

    ├── application:ports
    ├── foundation:units
    ├── foundation:domain
    ├── models:*
    └── Jackson Core
```

Прямые зависимости:

```kotlin
dependencies {
    implementation(project(":application:core"))
    implementation(project(":infrastructure:serialization"))

    testImplementation(kotlin("test"))
}
```

CLI не должен использовать внутренние классы Calculation Engine.

Если реализация envelope требует доступа к строгой JSON-инфраструктуре, необходимо использовать узкий публичный адаптер либо согласованное выделение общих компонентов.

Раскрытие внутренних JSON reader/writer исключительно ради обхода границ модулей запрещено.

## 33. Совместимость с GraalVM Native Image

CLI должен проектироваться с учётом последующей нативной компиляции.

Предпочтительные решения:

- явная регистрация моделей;
- явная регистрация кодеков;
- ручные JSON-мапперы;
- статически определённые контракты;
- ограниченное использование reflection;
- предсказуемая инициализация компонентов.

Следует избегать необоснованного использования:

- динамической загрузки классов;
- reflection-based сериализации;
- runtime code generation;
- динамических прокси;
- автоматического сканирования classpath.

Совместимость с GraalVM Native Image не считается подтверждённой до успешной нативной сборки и выполнения контрактных тестов.

## 34. Тестирование

### 34.1. Unit Tests

Необходимо проверить:

- разбор аргументов;
- Command Dispatcher;
- коды завершения;
- регистрацию ModelBinding;
- дубликаты идентификаторов;
- несовместимые типы кодеков;
- проверку версий;
- преобразование диагностики;
- преобразование ошибок;
- ограничения ресурсов.

### 34.2. Serialization Tests

Необходимо проверить:

- корректные запросы;
- корректные ответы;
- неизвестные поля;
- отсутствующие поля;
- явные null;
- повторяющиеся ключи;
- некорректные типы;
- trailing content;
- malformed UTF-8;
- BOM;
- signed zero;
- subnormal numbers;
- числовые переполнения;
- превышение размера;
- превышение глубины вложенности.

### 34.3. Integration Tests

Для каждой зарегистрированной модели необходимо проверить:

- получение дескриптора;
- получение схем;
- декодирование входных данных;
- успешную валидацию;
- отрицательную валидацию;
- успешный расчёт;
- обработку расчётного Failure;
- передачу предупреждений;
- сериализацию выходных данных.

### 34.4. Process Tests

Тестирование реального процесса должно включать:

- запуск установленного CLI;
- передачу данных через stdin;
- получение результата через stdout;
- независимое чтение stderr;
- проверку кодов завершения;
- проверку отсутствия лишнего вывода;
- закрытие входного потока;
- обработку повреждённых запросов;
- обработку превышения ограничений.

### 34.5. Contract Tests

Контрактные тесты должны проверять независимые JSON fixtures.

Ожидаемые результаты не должны генерироваться исключительно теми же сериализаторами, которые проверяются.

Необходимо подготовить:

- request fixtures;
- success response fixtures;
- failure response fixtures;
- negative fixtures;
- JSON Schema внешнего протокола.

### 34.6. Qt Integration Tests

После стабилизации CLI необходимо проверить:

- QProcess integration;
- асинхронное выполнение;
- корректную передачу UTF-8;
- сопоставление requestId;
- обработку exit codes;
- таймауты;
- остановку процесса;
- отклонение устаревших результатов.

## 35. Обратная совместимость

После публикации CLI Protocol V1 запрещается без изменения версии протокола:

- удалять обязательные поля;
- переименовывать поля;
- изменять типы существующих полей;
- изменять семантику статусов;
- изменять значения существующих кодов ошибок;
- изменять обязательные правила транспорта;
- изменять смысл кодов завершения;
- добавлять поля в закрытые структуры V1.

Добавление новых физических моделей не требует изменения версии протокола.

Добавление новой версии модельной схемы не требует изменения версии протокола при сохранении существующих правил её идентификации.

Несовместимые изменения требуют новой версии протокола.

## 37. Критерии готовности

CLI Protocol V1 считается готовым к публикации после выполнения следующих условий:

- реализованы обязательные команды;
- реализован типизированный каталог моделей;
- поддерживаются все шесть Legacy-моделей;
- доступны входные и выходные JSON Schema;
- реализован строгий UTF-8 транспорт;
- реализована проверка JSON envelope;
- сохраняется строгая семантика SnapshotCodec;
- реализованы стабильные коды ошибок;
- реализованы корректные exit codes;
- обеспечено разделение stdout и stderr;
- проверены ограничения ресурсов;
- реализованы unit tests;
- реализованы integration tests;
- реализованы process tests;
- реализованы contract tests;
- подтверждена совместимость с Qt через QProcess;
- проведён независимый архитектурный аудит;
- устранены блокирующие замечания;
- документация актуализирована и переведена на английский язык;
- опубликован релиз `cli-v1.0.0`.
